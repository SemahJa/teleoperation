# Per-arm mapping and recording

`robot_free.launch.py` completes the configurable per-arm mapper/recording
setup. It starts one mapper per entry in `arms.yaml`, an optional USB bridge,
an explicitly enabled synthetic measured-pose fixture, and an optional rosbag
recorder. It does not start an arm controller or gripper worker.

## Configuration

`src/quest_teleop/config/arms.yaml` keeps milestone 1 as one Panda assigned to
the right Quest controller. The mapper defaults remain trigger engage/release
0.75/0.25, 100 ms command timeout, 10 ms clock uncertainty, 10 Hz twist filter,
and feedforward scale 1.0. Existing freshness and re-engagement behavior applies
independently to each mapper.

Each arm can configure `namespace`, `base_frame`, `controller` (`left`/`right`),
`controller_state_topic`, `measured_pose_topic`, `command_topic`,
`target_pose_topic`, `state_topic`, `reference_to_robot_xyzw`, motion scales,
filter/blend parameters, clock gates, derivative intervals, and trigger
hysteresis. Relative topics resolve under the arm namespace. Raw input
defaults to the selected hand's `/quest_usb_bridge/{hand}/controller_state`.
Absolute topic overrides are supported.

Namespaces, base frames, measured-pose inputs, command/monitor outputs, and
nonempty future robot IPs must be distinct per arm. Topic aliasing between
measured-pose/raw inputs and mapper outputs is rejected. Nonfinite calibration,
invalid timing/gain/hysteresis values, and unknown config keys are rejected
before processes start. Hardware activation flags remain false in this
robot-free launch; `robot_ip` is metadata and is never used to connect.

`arms_two_mock.yaml` provides optional left/right namespaces for two synthetic
arms. Using it does not change the single-right-arm milestone acceptance scope.

## Calibration convention

`reference_to_robot_xyzw` is a unit quaternion representing `R_BQ`, the proper
rotation from Quest LOCAL vectors to that arm's robot base:

```text
robot_translation_delta = R_BQ * quest_translation_delta
robot_rotation_delta = R_BQ * quest_relative_rotation * transpose(R_BQ)
```

Quaternion order is x/y/z/w. The loader normalizes a finite nonzero quaternion.
This is a saved manual basis calibration; engagement supplies the translation
offset and measured robot orientation anchor. Identity is a software fixture
default, not a verified deployment calibration. OpenXR LOCAL has +X right,
+Y up, and -Z forward.

Save the measured basis separately for each arm. During later approved
commissioning, inspect isolated small controller translations along each
axis and small rotations, verify direction/sign/scale against the configured
robot base, then correct the saved basis if needed. Recenter resets clutch
anchors and requires trigger release/re-engagement; it does not estimate a
new calibration quaternion automatically.

## Run with the verified Quest app

Run these commands on the USB-connected PC. Reuse the existing APK and ADB
reverse workflow; no Android rebuild is needed. If the bridge is already
running, leave `start_bridge` at its default `false`.

PC terminal 1, from the repository:

```bash
cd /home/jiachun/franka_teleoperation
docker compose -f docker/compose.yaml run --rm --name quest-mapping-ros \
  panda-ros2 bash -lc \
  'source /opt/ros/humble/setup.bash && source /ws/install/setup.bash &&
   ros2 launch teleop_bringup robot_free.launch.py mock_measured_pose:=true'
```

If no USB bridge is running, add `start_bridge:=true` to that launch command.
The explicit mock fixture publishes a fresh fixed synthetic measured pose at
position `[0.4, 0.0, 0.4]` with identity orientation. It is not a robot model
and does not simulate physical dynamics or workspace limits.

PC terminal 2:

```bash
docker exec -it quest-mapping-ros bash
source /opt/ros/humble/setup.bash
source /ws/install/setup.bash
ros2 topic echo /panda_1/cartesian_teleop_command
```

With valid Quest input, release then hold the right trigger, move the controller,
and inspect target pose/twist. Release pauses motion; tracking/USB loss disarms;
recovery requires release/re-engagement. These commands have no FCI consumer.

For the two-arm mock configuration, add this launch argument in terminal 1:

```text
arms_config:=/ws/src/quest_teleop/config/arms_two_mock.yaml
```

Commands then appear on `/panda_left/cartesian_teleop_command` and
`/panda_right/cartesian_teleop_command`, driven by their corresponding controllers.

## Recording

Recording is off by default. Add `recording_enabled:=true` to the same launch
command to enable the optional profile in `config/recording.yaml`. It includes
each arm's raw controller state, commands, monitor pose, measured pose, robot
state, and future watchdog/gripper event topics. Unimplemented event/robot-state
publishers are not generated by this launch; currently available topics record
normally. Raw state already includes connection/focus/clock validity.

Each run gets a unique UTC-named bag directory under `/ws/log/quest_bags`, which
is mounted at `log/quest_bags` on the PC. Stop the launch with Ctrl+C to finalize
the bag metadata.

Replace the profile's topic list entirely via a JSON launch argument:

```text
recording_enabled:=true recording_topics:='["/quest_usb_bridge/right/controller_state", "/panda_1/cartesian_teleop_command"]'
```

Or copy/edit `recording.yaml`, set `include_default_topics: false`, put your
complete list under `topics`, and pass
`recording_config:=/ws/path/to/your-recording.yaml`. An empty enabled selection
is rejected. Recording can be disabled with `recording_enabled:=false`.

Set `recording_output_root:=/ws/log/my_experiment` to choose another mounted
output directory. Paths refer to the container; keeping them under `/ws`
preserves output through the existing repository mount. Topics are passed as
literal arguments, without shell expansion or automatic recording of all topics.

After stopping, inspect a selected bag from the ROS container:

```bash
ros2 bag info /ws/log/quest_bags/ACTUAL_BAG_DIRECTORY
```
